# 平台上下文：内核态 vs 裸机固件

同一个 C 写法在两个环境里结论可能相反。审阅前必须先确定模式；两种模式都不能靠猜。

## 先问的五个问题

1. 目标平台与阶段：Linux 内核？BROM / BL2 / BL31 / U-Boot？RTOS？
2. MMU 与 cache：关、开、还是部分（如 BL2 只开 D-cache）？
3. 内存模型：有 `malloc` 吗？堆从哪来？栈多大？
4. 并发源：多核？中断？DMA？有没有调度器？
5. 能否调试：串口可用吗？哪一级开始有日志？

答不出第 1、2 项，不下“性能/优化”类结论，只做语言级与逻辑级审查。

## 模式 A：Linux 内核

| 维度 | 规则 |
|---|---|
| 分配 | `kmalloc` 带正确的 GFP：可睡眠上下文 `GFP_KERNEL`，原子上下文 `GFP_ATOMIC`，DMA 用 `dma_alloc_coherent` |
| 锁 | 进程上下文用 `mutex`；中断共享用 `spin_lock_irqsave`；读多写少用 `rwlock`/RCU；能睡眠的临界区禁止自旋锁 |
| 上下文 | 硬中断不能睡眠、不能 `copy_to_user`、不能拿 `mutex`；软中断同理 |
| 硬件 | `readl/writel` 加 `__iomem`；`ioremap` 后的指针不得直接解引用 |
| 用户态 | `copy_from_user` / `copy_to_user` 必须检查返回值；避免 `get_user` 与 `put_user` 的类型错误 |
| 引用 | `of_node`、`clk`、`regulator`、`gpiod`、`device` 的 get/put 必须配对 |
| 并发初始化 | `module_init` 期间的全局量无需锁，但热插拔/延迟探测后不再是 |
| 类型标注 | `sparse` 的 `__user`、`__iomem`、`__rcu`、`__percpu` 必须加对，否则掩盖真实 bug |
| 栈 | 默认 16KB（含中断嵌套），局部数组 > 512 字节就要重新考虑 |

常见内核特有缺陷：`probe` 失败路径漏 `clk_disable_unprepare`；`remove` 后工作队列仍在使用 `dev`；`copy_to_user` 在持锁时调用；`devm_*` 与手动释放混用导致双重释放。

## 模式 B：裸机 / Bootloader（BROM → BL2 → BL31 → U-Boot）

以 MT7987 这类 ARMv8-A + TF-A + U-Boot 的启动链为参照（依据：项目内《MT7987 BootROM 到 FIP 的签名与验证流程》）。

| 阶段 | 可用资源 | 约束 |
|---|---|---|
| BROM | 芯片内固化，不可修改 | 无日志、无调试；失败即黑砖；只验证 `bl2.img` 的 header + payload |
| BL2 | 固定 SRAM 布局，无堆或极小堆 | 串口可能可用；需自行实现 `memcpy`/`memset`；栈通常几 KB |
| BL31 | TF-A 运行时 | 有 exception level 切换与 PSCI；注意 `x0-x30` 保存约定 |
| BL33 (U-Boot) | 有驱动模型与较完整运行时 | 内存已初始化，但仍受早期栈与重定位约束 |

裸机硬规则：

- **MMIO 必须 `volatile`**（或 `readl`/`writel` 等价封装），否则编译器会合并或删除访问。
- **寄存器写后立刻读状态**需要 `dsb`/`isb`；写门铃、开中断、跳转前必须有屏障。
- **cache 维护按 VA 做 clean/invalidate**；DMA 缓冲区必须与非 cache 访问严格分离；先 clean 再交硬件，拿回所有权后 invalidate。
- **无 `malloc`**：缓冲区来自静态数组、链接脚本段或专用内存池；每个缓冲区都要在注释里写大小上限。
- **无 libc**：`memcpy`/`memset`/`strlen` 要么自带，要么确认可链接；不要假设 `printf` 存在。
- **栈极小**：禁止大局部数组、递归、可变长数组；深调用链要在注释里标明。
- **对齐**：ARMv8 上未对齐访问的容忍度与配置相关，不要依赖；packed 成员一律 `memcpy` 出来用。
- **看门狗**：长耗时操作（擦除、校验、大块解密）必须喂狗或分段处理。

启动链特有的安全约束：

- **先验证，后解析**：任何来自 flash / FIP / 外部输入的头部字段，在签名验证通过前不得用于计算长度、偏移或分配。
- **验证顺序不可优化**：信任链逐级建立，跳过一级校验等于移除信任锚。
- **eFuse 写入不可逆**：涉及烧写的代码路径必须做“已烧写”检查，且不可放在自动化流程里。
- **失败即停**：BROM 阶段失败无输出，因此代码里任何“忽略错误继续”的写法在该阶段都是 P0。

## 两种模式都适用的判定

| 现象 | 结论 |
|---|---|
| `volatile` 当锁用 | P0，`volatile` 不提供原子性与顺序保证 |
| 结构体直接 `memcpy` 到寄存器 | P0，布局与对齐都不成立 |
| 用 `int` 存指针或地址 | P0，64 位平台截断 |
| 写寄存器前不读手册 | 结论只能到“待确认”，要求提供手册页 |
| 错误路径只 `return` 不清理 | P1，裸机里还可能是 P0（状态不一致导致后续阶段异常） |

## 传输给审阅结论的措辞

- 内核：结论可以直接到“这里在软中断上下文睡眠，会导致 `BUG: scheduling while atomic`”。
- 裸机：结论要限定到阶段与配置——“在 BL2 关 MMU、D-cache 关闭的配置下，这里没问题；一旦开启 D-cache，DMA 缓冲区必须按 VA 做 clean”。
- 跨阶段代码：先确定它跑在哪个阶段，再判。同一段 `memcpy` 在 BL31 与 BL2 里的风险等级不同。
